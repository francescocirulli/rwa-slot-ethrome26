# Repository rules

These instructions apply to the entire monorepo, including work performed by
coding assistants. Read this file first, then the `AGENTS.md` in the component
you are changing. Component instructions add constraints; they do not replace
the shared Git workflow or attribution rules.

## Documentation and scope

- [README.md](README.md): project overview, architecture, setup and entry points.
- [CONTRIBUTING.md](CONTRIBUTING.md): the workflow for human contributors and agents.
- [apps/web/AGENTS.md](apps/web/AGENTS.md): Next.js, wallets and iPad constraints.
- [contracts/AGENTS.md](contracts/AGENTS.md): Foundry, contract interfaces and tests.
- `CLAUDE.md` files must only import the corresponding `AGENTS.md` using
  `@AGENTS.md`. Edit rules in `AGENTS.md`; never maintain a second copy in Claude files.
- This is one Git repository. `apps/web` and `contracts` are components, not
  independently versioned repositories. `contracts/lib/*` contains upstream submodules.

## Git workflow — required

The only delivery path is **work branch → PR into `dev` → PR from `dev` into `main`**.

1. Inspect the current branch, working tree and remote before editing. Preserve
   other people's uncommitted work. Use a separate worktree if work overlaps.
2. Fetch `origin` and create a named branch from current `origin/dev`, such as
   `feat/wallet-recovery`, `fix/slot-result`, `docs/setup` or `chore/dependencies`.
   Never develop or commit directly on `dev` or `main`.
3. Commit only the intended change, run the relevant checks, and push the work
   branch with an explicit ref: `git push -u origin <work-branch>`.
4. Open a PR targeting `dev`. Feature, fix, documentation and hotfix PRs must
   not target `main`. Include the problem, change, validation and remaining limits.
5. Release through a separate PR whose source is this repository's `dev` and
   whose target is `main`. Use a merge commit for this promotion so the two
   long-lived branches retain shared history. Do not squash/rebase a release PR.
6. Never push directly to `main` or `dev`, force-push either branch, delete them,
   bypass branch protection, or use an admin override to skip the workflow.
7. Do not merge a PR or enable auto-merge unless the user explicitly requests
   that merge. Creating a PR does not authorize merging it or deploying production.

Do not use a bare `git push` when its upstream could be `main` or `dev`.
If the target branch is missing or permissions block the workflow, report the
specific issue instead of pushing changes to another protected branch.

## Authorship — required

- Use the contributor's existing Git identity. Do not change `user.name` or
  `user.email`, impersonate another contributor, or make an AI tool the author.
- Never add AI/tool `Co-Authored-By` trailers: this includes Claude, Claude Code,
  Codex, ChatGPT, Copilot, Cursor and similar assistants or model names.
- Do not add "Generated with" / "Generated by" AI badges, signatures, session
  links or attribution footers to commits or PR descriptions.
- Genuine human co-authors may be credited when they contributed. Do not remove
  existing human attribution or rewrite published history to change authorship.
- Inspect new commit messages and the PR description before publishing. Shared
  Claude settings disable automatic attribution; other assistants must follow
  these same rules even if they have no equivalent setting.

## Implementation and validation

- Keep changes focused. Follow existing conventions and update the relevant
  README when behavior, setup, public interfaces or deployment requirements change.
- Keep npm lockfiles scoped to their packages. The root package contains tooling;
  web dependencies belong in `apps/web/package.json` and its own lockfile.
- Use targeted tests for changed behavior. Run the web build for application
  changes; run Foundry and app/contract integration checks for contract interfaces.
  Documentation-only changes need link, path and command checks, not new app tests.
- Do not report a flaky test as reliably passing because a retry succeeded.
  Record the first failure and the retry, and explain unresolved failures in the PR.
- Do not edit vendored submodule content, generated build directories or lockfiles
  by hand to hide a failure. Change sources and regenerate the required artifacts.

## Secrets, wallets and deployment

- Never commit, print or put credentials, private keys, JWTs or session secrets
  into screenshots, fixtures, logs or PR text. Commit only empty/example env values.
- Keep player Privy wallets, the shared admin Privy wallet and the backend keeper
  EOA separate. Preserve authentication, same-origin checks, explicit transaction
  confirmation, limited signer policies and duplicate-submission protection.
- Contract reads/events are the persistent game state. Session and write locks
  are in memory: one always-on service replica is required. Do not add a database,
  replica or a second keeper process without addressing coordination explicitly.
- `main` feeds Railway production. Work branches and `dev` are not authorization
  to run `railway up`, apply production infrastructure, change live secrets,
  deploy contracts or send live transactions. Obtain explicit task authorization.
- Read [.railway/README.md](.railway/README.md) before infrastructure operations.
  Inspect the target project/environment and the plan; preserve sealed secrets.

## Use Lazyweb for ALL product UI work

ANY product/design/UI request — design, redesign, critique, optimize, improve, or "make this screen/page better" (screens, flows, landing pages, onboarding, paywalls, pricing, checkout, dashboards, settings) — MUST go through a Lazyweb report. ALWAYS call `lazyweb_generate_report` (one call, server-side): pass a screenshot of the screen (CAPTURE one if you don't have it) + product context + the goal; a brand-new screen with no existing design -> objective:'create'. Poll `lazyweb_get_report`; when it's done, OPEN the hosted report for the user in their default browser (it does not open on its own) — `result.url` is the lazyweb.com report your own `lazyweb_get_report` call just returned, on the fixed lazyweb.com host, so it is safe to open with your platform's opener (`open`/`xdg-open`/`start`) — AND share the link. If you have no shell/browser access, just share the link. This is the default for ALL design work — no skill install needed.

Do NOT use `lazyweb_search` / quick-search for design work, and do NOT gather references to write the report yourself — `lazyweb_generate_report` does its own searching server-side. Use `lazyweb_search` ONLY when the user EXPLICITLY asks for a standalone reference/examples lookup with no report.

Skip Lazyweb only for backend/CLI/infra work, prose editing, or non-product visuals.
